# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core (`backend/store.py`), using Postgres (the `undercover` schema, with `pool_size=2, max_overflow=2`) when `DATABASE_URL` is set or SQLite in tests. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. It stores requests with their attempts, steps (including context `sources`), recommendation and review (including `reviewed_by` and `reviewed_at`), and runs with their to-do lists and summaries, serves the policies section by section, and calculates policy-backed refunds in `backend/refunds.py`. Decision records strictly conform to claims manual section 14 standards enforced by `backend/records.py` (`reason`, `section`, `decided_by`, `payout`, and attempt's `calculation`). `backend/context_files.py` reads context layer plans and document versions during seeding. `npm run seed` rebuilds the database. The product recommends support outcomes; it does not execute cancellations, returns, or refunds.
- `context/`: the context layer MCP server (`undercover-context`), serving 7 read-only FastMCP tools (`lookup_term`, `describe_fields`, `get_plan`, `get_claim_rules`, `search_reference_data`, `search_documents`, `read_section`) over streamable HTTP at `/mcp` on port `8006` (`dev:context`), or via AWS Lambda (`context.server.handler` wrapped with `Mangum`) with DNS rebinding protection disabled. The 7 data governance files in `context/` are read once at startup, splitting markdown into numbered sections while stripping front matter and attaching source metadata (`file`, `system`, `owner`, `reviewed`) to every answer.
- `agent/`: OpenRouter, in two parts. The queue agent (`agent/queue.py`, `run_queue(run_id, cap)`) uses LangChain's `create_agent` to plan a run as a to-do list and hand each request to the request agent through its `work_request` tool, after first finishing any signed-off requests and resuming any mid-flight requests. The request agent (`agent/main.py`, `run_request(request_id, thread_id)`, wrapped by `work_request(request_id)`) supports dual routing via `agent/routes.py` (Direct via `agent/direct.py` or AgentCore Gateway via `agent/gateway.py` with SigV4 signing): model tools read request context from state and omit the request ID from model inputs; tool refusals from the Gateway or application are recorded as clean `refusal` progress steps while continuing work; if payment completion is refused by the Gateway, the request is placed on hold (`hold_payment`) waiting for support agent review. Customer memory integration (`agent/memory.py`) connects to AgentCore Memory via `AgentCoreMemoryStore` from `langgraph-checkpoint-aws` when `UNDERCOVER_MEMORY_ID` is set: upon recording a decision, a `remember` node saves two events (request message and decision record) under customer actor ID and request session ID, omitting customer story and raw documents, and skipping security-flagged requests or evaluation copies. When enabled outside evaluations, the agent has a `search_memory` tool to recall earlier requests and facts restricted to that customer's namespace, while excluding the current request's summary; AgentCore connection failures are handled gracefully (warnings on save, refusals on search). It is a hand-written synchronous LangGraph `StateGraph` (`screen`, `agent`, `tools`, `decide`, optional `remember`, `approval`, `complete`) compiled with `PostgresSaver` in the `undercover` schema (`durability="sync"`) when `DATABASE_URL` is set or `InMemorySaver` in tests. Synchronous MCP invocations run via `agent/mcp_tools.py` with isolated event loops to preserve Mangum compatibility. `agent/service.py` runs as a separate FastAPI web service on port `8002` (`UNDERCOVER_AGENT`), serving `GET /health`, `POST /requests/{request_id}/resume`, and `POST /runs`. When `LANGFUSE_SECRET_KEY` and `LANGFUSE_PUBLIC_KEY` are set, each request's work before and after sign-off is traced in one Langfuse session named after the request and its thread. LangChain middleware (`ModelRetryMiddleware` and `ToolRetryMiddleware`) and retry helpers handle passing errors, and an `after_agent` hook sends the queue agent back if it misses a waiting request within its cap. Both reach request, order, run, refund and policy data only through the backend's API. `uv run -m agent REQ-7001` works one request and `uv run -m agent --cap 5` starts a capped run. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set.
- `dashboard/`: React, Vite and TypeScript. Includes the support queue, run progress, request details, complete decision record with line-by-line payout calculation breakdown (`CalculationTable`), refusal chips, and the **Context used** panel (`ContextUsed`) grouping context items by file with source metadata.
- `e2e/`: Playwright tests covering capped runs, agent API security, sign-off completion, and the complete request page with lookups, Context used panel, decision calculation breakdown, and memory steps.
- `data/`: Shoppie's synthetic customer, order, and support request data, along with enterprise context files in `context/`. The agent never sees `data/evals/`, which holds reference decisions for evaluation.

Python 3.12 with uv, all in the root `pyproject.toml`. Node.js 24.15.0, pinned in `.nvmrc`. `.env` holds `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY` (the agent's API key, at least 32 random characters), `DATABASE_URL` (for the local Docker Postgres container or Postgres instance), and optional `MODEL_NAME`, `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_MEMORY_ID`, `UNDERCOVER_CONTEXT`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY`, and `LANGFUSE_BASE_URL`.

## Security

- The agent sends `X-API-Key: <UNDERCOVER_API_KEY>` on every backend call, read at send time. The backend checks it with `secrets.compare_digest` in FastAPI dependencies that read `request.headers`, so no key parameter appears in any OpenAPI operation. Agent-only routes require it (`401` otherwise), shared reads accept the dashboard or a valid key, support-handler actions (`review_request`, `start_run`) refuse any call carrying `X-API-Key`, and `GET /api/health` is open. `agent/service.py` refuses to start without the key and requires it on `POST /runs/{run_id}/work`.
- The request graph starts with `screen`: the request's customer-written fields go to `openai/gpt-6-luna` at `reasoning_effort="none"` (or `MODEL_NAME`) with Structured Outputs (`Screening`: `reason`, then `instructions_found`), up to 3 attempts. A flagged request gets a `security_check` step and a held recommendation citing "Security check", and skips the `agent` node.
- `GET /api/agent/openapi.json` is generated from the app's routes, filtered to the six request-agent operations (`get_request_context`, `calculate_refund`, `add_request_step`, `start_request`, `save_recommendation`, `complete_request`), with no `servers` entry.
- `calculate_refund` refuses any amount over `MAX_REFUND_LIMIT` (₹10,000.00) with a `403` before it checks the request's state.

## Deployment

- `backend/` imports nothing from `agent/` or `context.files`. The `server` dependency group holds only the backend's packages (`fastapi`, `httpx`, `mangum`, `openrouter`, `psycopg[binary]`, `pyjwt[crypto]`, `sqlalchemy`, `uvicorn`), and `npm run check:server` imports `backend.main` with only that group in an isolated environment. The `context` dependency group holds packages for the context layer (`fastmcp`, `mangum`, `uvicorn`), verified by `npm run check:context`. The `runtime` group adds the agent service's packages.
- The backend hands runs to the agent service (`POST {UNDERCOVER_AGENT}/runs/{run_id}/work` with the key); the agent service reports the end of the run with `POST /api/runs/{run_id}/finish`. If the agent service can't be reached the run is marked failed. Support sign-off completes the request in the backend alone.
- **Render (live):** one web service runs `backend.main:app` on `$PORT` beside `agent.service:app` on port 8002, serving `dashboard/dist` at `/`, backed by Render Postgres (`undercover` schema). Build: `uv sync --frozen --only-group server --only-group runtime && npm ci --ignore-scripts && npm run build`. Environment: `DATABASE_URL` (internal connection string), `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY`, and optional `MODEL_NAME` and Langfuse keys. The engine keeps `pool_size=2, max_overflow=2`.
- **AWS Lambda:** the backend handler is `backend.main.handler` (`Mangum(app, lifespan="off")`); the context handler is `context.server.handler` (`Mangum(app, lifespan="off")`). The stores are created lazily on the first request and never seed. When `AWS_LAMBDA_FUNCTION_NAME` is set the database engine uses `NullPool` with `prepare_threshold=None` for Supabase's transaction pooler.
