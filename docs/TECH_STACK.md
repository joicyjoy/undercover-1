# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core (`backend/store.py`), using Postgres (the `undercover` schema, with `pool_size=2, max_overflow=2`) when `DATABASE_URL` is set or SQLite in tests. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. It stores requests with their attempts, steps, recommendation and review (including `reviewed_by` and `reviewed_at`), and runs with their to-do lists and summaries, serves the policies section by section, and calculates policy-backed refunds in `backend/refunds.py`. `npm run seed` rebuilds the database. The product recommends support outcomes; it does not execute cancellations, returns, or refunds.
- `agent/`: OpenRouter, in two parts. The queue agent (`agent/queue.py`, `run_queue(run_id, cap)`) uses LangChain's `create_agent` to plan a run as a to-do list and hand each request to the request agent through its `work_request` tool, after first finishing any signed-off requests and resuming any mid-flight requests. The request agent (`agent/main.py`, `run_request(request_id, thread_id)`, wrapped by `work_request(request_id)`) is a hand-written synchronous LangGraph `StateGraph` (`screen`, `agent`, `tools`, `decide`, `approval`, `complete`) compiled with `PostgresSaver` in the `undercover` schema (`durability="sync"`) when `DATABASE_URL` is set or `InMemorySaver` in tests. It works one request on a checkpointed thread per attempt (`{request_id}-attempt-{attempt}`), pauses at `approval` with `interrupt()`, and completes the request in `complete` when resumed after support sign-off. `agent/service.py` runs as a separate FastAPI web service on port `8002` (`UNDERCOVER_AGENT`), serving `GET /health`, `POST /requests/{request_id}/resume`, and `POST /runs`. When `LANGFUSE_SECRET_KEY` and `LANGFUSE_PUBLIC_KEY` are set, each request's work before and after sign-off is traced in one Langfuse session named after the request and its thread. LangChain middleware (`ModelRetryMiddleware` and `ToolRetryMiddleware`) and retry helpers handle passing errors, and an `after_agent` hook sends the queue agent back if it misses a waiting request within its cap. Both reach request, order, run, refund and policy data only through the backend's API. `uv run -m agent REQ-7001` works one request and `uv run -m agent --cap 5` starts a capped run. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests.
- `data/`: Shoppie's synthetic customer, order, and support request data. The agent never sees `data/evals/`, which holds reference decisions for evaluation.

Python 3.12 with uv, all in the root `pyproject.toml`. Node.js 24.15.0, pinned in `.nvmrc`. `.env` holds `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY` (the agent's API key, at least 32 random characters), `DATABASE_URL` (for the local Docker Postgres container or Postgres instance), and optional `MODEL_NAME`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY`, and `LANGFUSE_BASE_URL`.

## Security

- The agent sends `X-API-Key: <UNDERCOVER_API_KEY>` on every backend call, read at send time. The backend checks it with `secrets.compare_digest` in FastAPI dependencies that read `request.headers`, so no key parameter appears in any OpenAPI operation. Agent-only routes require it (`401` otherwise), shared reads accept the dashboard or a valid key, support-handler actions (`review_request`, `start_run`) refuse any call carrying `X-API-Key`, and `GET /api/health` is open. `agent/service.py` refuses to start without the key and requires it on `POST /runs/{run_id}/work`.
- The request graph starts with `screen`: the request's customer-written fields go to `openai/gpt-6-luna` at `reasoning_effort="none"` (or `MODEL_NAME`) with Structured Outputs (`Screening`: `reason`, then `instructions_found`), up to 3 attempts. A flagged request gets a `security_check` step and a held recommendation citing "Security check", and skips the `agent` node.
- `GET /api/agent/openapi.json` is generated from the app's routes, filtered to the eight request-agent operations, with no `servers` entry.
- `calculate_refund` refuses any amount over `MAX_REFUND_LIMIT` (₹10,000.00) with a `403` before it checks the request's state.

## Deployment

- `backend/` imports nothing from `agent/`. The `server` dependency group holds only the backend's packages (`fastapi`, `httpx`, `mangum`, `openrouter`, `psycopg[binary]`, `pyjwt[crypto]`, `sqlalchemy`, `uvicorn`), and `npm run check:server` imports `backend.main` with only that group in an isolated environment. The `runtime` group adds the agent service's packages.
- The backend hands runs to the agent service (`POST {UNDERCOVER_AGENT}/runs/{run_id}/work` with the key); the agent service reports the end of the run with `POST /api/runs/{run_id}/finish`. If the agent service can't be reached the run is marked failed. Support sign-off completes the request in the backend alone.
- **Render (live):** one web service runs `backend.main:app` on `$PORT` beside `agent.service:app` on port 8002, serving `dashboard/dist` at `/`, backed by Render Postgres (`undercover` schema). Build: `uv sync --frozen --only-group server --only-group runtime && npm ci --ignore-scripts && npm run build`. Environment: `DATABASE_URL` (internal connection string), `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY`, and optional `MODEL_NAME` and Langfuse keys. The engine keeps `pool_size=2, max_overflow=2`.
- **AWS Lambda:** the handler is `backend.main.handler` (`Mangum(app, lifespan="off")`); the store is created lazily on the first request and never seeds. The package is `backend/` (without tests), `data/`, `dashboard/dist/` and the `server` group's wheels for Linux and Python 3.12 (19 MB zipped). When `AWS_LAMBDA_FUNCTION_NAME` is set the engine uses `NullPool` with `prepare_threshold=None` for Supabase's transaction pooler.
