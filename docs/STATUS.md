# Status

The Shoppie pilot, its harness (`docs/HARNESS.md`, `docs/PLAN_HARNESS.md`), durable state (`docs/DURABLE.md`, `docs/PLAN_DURABLE.md`), security / deployment (`docs/SECURE.md`, `docs/PLAN_SECURE.md`), the context layer and Gateway integration, claims manual section 14 decision records, and customer memory integration (`docs/CONTEXT.md`, `docs/PLAN_CONTEXT.md`) are implemented:

- `backend/`: health, SQLAlchemy Core seed and repository (`backend/store.py`, supporting Postgres with the `undercover` schema and capped connection pools when `DATABASE_URL` is set, or SQLite in offline tests, and `NullPool` with `prepare_threshold=None` when `AWS_LAMBDA_FUNCTION_NAME` is set), request list/detail, the request context, policies served section by section (`GET /api/policies` and `read_policy_section`, which records each section read on the request), policy-backed refund calculation (`POST /api/requests/{request_id}/refund` capped at ₹10,000.00 approval limit, tracking calculations in a `calculations` table per request attempt), read-only instructions for the queue and for a request, and claims manual section 14 deterministic validation (`backend/records.py`, `backend/money.py`): validates non-empty reason, section, and decided_by, requires approvals to have payout > 0 matching the attempt's calculation on file, and enforces payout = 0 on declines/referrals, refusing non-compliant records with HTTP 422 naming section 14. Idempotent agent operations start a waiting request, store its complete recommendation (persisting `decided_by`, `manual_version`, `calculation`, and `decided_at`), record support sign-off (`POST /api/requests/{request_id}/review` with `reviewed_by`, moving requests directly to `decided` on the backend and notifying `UNDERCOVER_AGENT`), complete a reviewed request (`POST /api/requests/{request_id}/complete`), hold a request whose payment was refused by the Gateway (`POST /api/requests/{request_id}/hold`, `operation_id="hold_payment"`), or count a failed attempt. Runs (`POST /api/runs` with a cap, `GET /api/runs/current`, `PUT /api/runs/{run_id}/todos`, `POST /api/runs/{run_id}/todos/{request_id}`, `POST /api/runs/{run_id}/finish`) keep a to-do list and a summary, and only one runs at a time. The backend imports nothing from `agent/`, exposing `handler = Mangum(app, lifespan="off")` with lazy `Store()` initialization. The agent's standalone API schema is published at `GET /api/agent/openapi.json` with exactly 6 operations. Every agent route requires `X-API-Key: <UNDERCOVER_API_KEY>`, while support-handler actions reject requests carrying the agent key. `backend/context_files.py` reads plans and document versions directly from `context/` during seeding without importing `context.files`. `npm run seed` rebuilds the database with 9 requests (including `REQ-7901` from `data/security/customer_orders.json`).
- `context/`: the context layer MCP server (`undercover-context`), serving 7 read-only FastMCP tools (`lookup_term`, `describe_fields`, `get_plan`, `get_claim_rules`, `search_reference_data`, `search_documents`, `read_section`) over streamable HTTP at `/mcp` on port `8006` (`dev:context`), or via AWS Lambda (`context.server.handler` wrapped with `Mangum`) with DNS rebinding protection disabled. The 7 data governance files in `context/` are read once at startup, splitting markdown into numbered sections while stripping front matter and attaching source metadata (`file`, `system`, `owner`, `reviewed`) to every answer. `check:context` verifies isolated execution with the `context` dependency group.
- `agent/`: the queue agent (`agent/queue.py`, `run_queue(run_id, cap)`, `work_run(run_id, cap)`) uses LangChain's `create_agent` to plan a run as a to-do list and hand each request to the request agent with `work_request`, after first finishing any signed-off requests and resuming any mid-flight requests, then reports run completion to `POST /api/runs/{run_id}/finish`. Code enforces the cap and ticks the to-do list, and an `after_agent` middleware sends the agent back if it misses a waiting request within the cap. The request agent (`agent/main.py`) supports dual routing via `agent/routes.py` (Direct via `agent/direct.py` or AgentCore Gateway via `agent/gateway.py` with SigV4 signing): model tools read request context from state and omit the request ID from model inputs; tool refusals from the Gateway or application are recorded as clean `refusal` progress steps while continuing work; if payment completion is refused by the Gateway, the request is placed on hold (`hold_payment`) waiting for support agent review. Customer memory integration (`agent/memory.py`) connects to AgentCore Memory via `AgentCoreMemoryStore` from `langgraph-checkpoint-aws` when `UNDERCOVER_MEMORY_ID` is set: upon recording a decision, a `remember` node saves two events (request message and decision record) under customer actor ID and request session ID, omitting customer story and raw documents, and skipping security-flagged requests or evaluation copies. When enabled outside evaluations, the agent has a `search_memory` tool to recall earlier requests and facts restricted to that customer's namespace, while excluding the current request's summary; AgentCore connection failures are handled gracefully (warnings on save, refusals on search). It is a hand-written synchronous LangGraph `StateGraph` (`screen`, `agent`, `tools`, `decide`, optional `remember`, `approval`, `complete`) compiled with `PostgresSaver` when `DATABASE_URL` is set or `InMemorySaver` in tests: it screens customer text for hidden instructions using `openai/gpt-6-luna` (holding prompt injections citing "Security check" without invoking the main agent model), reads the context, looks up only the policy sections it needs, calculates eligible refunds with `calculate_refund`, saves a structured recommendation in `decide` (with safety overrides for ambiguous cancellations and food-safety cases), pauses at `approval` with `interrupt()`, and completes the request in `complete` when resumed after support sign-off. If stopped partway through an attempt, it resumes from its last checkpoint on the same thread without incrementing `attempts`. Synchronous MCP invocations run via `agent/mcp_tools.py` with isolated event loops to preserve Mangum compatibility. `agent/service.py` runs as a separate FastAPI web service on port `8002` (`GET /health`, `POST /requests/{request_id}/resume`, `POST /runs`, `POST /runs/{run_id}/work`). When `LANGFUSE_SECRET_KEY` and `LANGFUSE_PUBLIC_KEY` are set, each request's work is traced in one Langfuse session named after the request and its thread. Model and transport calls are retried automatically, and a single attempt is capped at 30 model calls. The default model is DeepSeek V4.1 Flash with low reasoning effort; `MODEL_NAME` overrides it. `uv run -m agent --cap 5` starts a capped run, and `uv run -m agent REQ-7001` works one request.
- `dashboard/`: the support queue with a "Requests to work" cap and an Initiate processing button that starts a run. The run panel shows the to-do list (to do, in progress, done, left for support) and the summary. Queue badges show each request's agent decision, its reviewed outcome, or "Left for support". The request detail shows the recommendation, the progress timeline and the policy sections read, with the support review form (including a required "Reviewed by" field) and the recorded reviewer and timestamp once signed off. Polling continues while a signed-off request is in progress until the agent completes it. The instructions panel shows the queue and request instructions, read only.
- `data/`: synthetic Shoppie customer, order, and support request records, including clearly labeled synthetic follow-ups, photo, packing, delivery and carrier evidence for every request, and a fulfillment timeline (plus shipment tracking once dispatched) on every order. `data/security/customer_orders.json` provides `REQ-7901` to test the hidden-instruction check. Food and perishable cases are limited to the leafy greens cancellation and the missing bread report; the food-safety guardrail is covered by a unit test fixture.
- `docs/`: Shoppie's sample shopping, cancellation, and returns policies, which the agent reads section by section.
- `data/evals/`: reference decisions kept separate from agent-readable data.

Agent recommendations support review; the product does not execute real customer or order actions. The dashboard displays INR values and IST times for the synthetic records.

## Running it

Run `uv sync` and `npm install` at the repository root. Start the local Postgres container (`shoppie-postgres` on `127.0.0.1:5432`, with `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5432/postgres` and `UNDERCOVER_API_KEY` in `.env`), run `npm run seed` to reset the `undercover` schema, and run `npm run dev` to start the backend (`:8000`), the agent service (`:8002`), and the dashboard (`:5173`). `npm run build` builds the dashboard into `dashboard/dist`, which `backend.main:app` serves at `/` on a web server such as Render. Start a run from the dashboard, or with `uv run -m agent --cap 5` while `npm run dev` is running. For trials on the real model, reseed first and cap the run at five requests.

The Linux Python 3.12 Lambda deployment package (`backend/`, `data/`, `dashboard/dist/`, and `--only-group server` wheels) produces a zip of 19 MB (74 MB uncompressed), well inside AWS Lambda's 50 MB direct upload and 250 MB unzipped limits.
